## D-004｜2026-05-22｜Experience Flywheel 構造を採用

**決定：** システムは Sense → Generate → Reach → Learn の4層自律サイクルとして設計する（Google Reason-Act-Observe ループに準拠）。

**参照：** [BusinessInsider — AI 自律型経営](https://www.businessinsider.jp/article/2605-where-ai-stands-today-ep2/?page=2)

**理由：**
- 単発ツールではなく、ループで進化するシステムにする
- Sense と Learn が無いとデザインは「作って終わり」になる
- 既存資産（Insight Engine / 自動レポート）が部分的に Sense を担っているので接続できる

**含意：** 各層を「独立して動くが、相互に繋がる」設計にする

---

## D-005｜2026-05-22｜最小ホイール（MVF: Minimum Viable Flywheel）から始める

**決定：** 全層を最初から完璧に作らず、「最小だけど確実に1周回るホイール」を最初に作る。

**理由：**
- 各層が単体で動いても、繋がらないと意味がない
- 1周回ってからの方が「どこを強化すべきか」が見える
- 既存資産（Sense 部分稼働、Generate 高完成度）を活かして早期に1周回せる

**最小ホイールの構成：**
- Sense（最小）：既存 Insight Engine + 月次ダッシュボード手動読み
- Generate（マレル向け）：Claude Brand Brain + Canva / Figma テンプレ
- Reach（既存）：Shopify / SNS / メール 手動配信
- Learn（最小）：使用記録 + 月1振り返り

## D-006｜2026-05-22｜Brand Layer と Engine Layer を完全分離

**決定：** FAMBOX 固有情報は `brand/fambox/*` に閉じ込め、エンジン層には埋め込まない。

**理由：**
- マルチブランド化の布石（FAMBOX 完成後に Brand B を追加できるように）
- ブランドが進化しても、エンジン側のコード変更を最小化

**含意：**
- エンジン層で「色を生成する時は brand.tokens.colors を参照する」など、すべて変数経由
- FAMBOX 固有の文字列リテラルをコードに書かない

## D-007｜2026-05-22｜DS は 4階層で抽象化

**決定：** Design System を `tokens / components / patterns / templates` の4階層で構成する。

**理由：**
- マルチブランド化時、4階層の中身（値）だけを入れ替えれば動く構造にする
- 業界標準（Tailwind / shadcn / Linear DS など）と整合

**含意：** マルチブランド化を意識した命名規則・ディレクトリ構造を Phase 1 から徹底する

## D-009｜2026-05-22｜永続化システムを最初に構築

**決定：** Phase 1 着手の前に、`docs/okr/fambox-flywheel/` ディレクトリ + memory ファイルで構想を永続化する（このディレクトリ自体）。

**理由：**
- 長期プロジェクト（半年〜2年）なので、文脈消失リスクが最大
- セッション断絶からの復帰機能が無いと、毎回ゼロから議論することになる
- ユーザー自身が「いつでも確認できる」状態を保ちたい

**含意：**
- すべての議論・決定をこのディレクトリに記録
- セッション毎に sessions/ に議事録
- 私（Claude）は新セッション開始時に memory ファイル → このディレクトリの順で読む

## D-011｜2026-05-26｜ウォーターフォール → 週次マイクロデリバラブルへ（D-005 の改訂）

**決定：** Phase 単位（1ヶ月のかたまり）ではなく、**1週間に1個の具体的成果物** を積み上げる方式に変える。

**運用：**
- **月曜**：今週の1個を決める + retrospect
- **火〜木**：実作業（環境組み + 制作 + マークから盗む）

**理由：**

- 1か月のかたまりで作ると、初期前提のミスが後で発覚しても巻き戻しに時間がかかる
- 週次なら 4週間で 4回軌道修正できる
- マーク達のチーム会レビュー文化（緊張感）が宮川さん側にない → これを金曜事業開発に持ち込む

**含意：**
- D-005（MVF 最小ホイール）は **「最小だけど確実に1周回るホイール」ではなく「最小の1個のリニア成果物」** に変更
- 円形化は当面棚上げ。Step 3 で取り組む
- PROGRESS.md のフェーズ構造を週次タスクリストに変える（Week 1 から順次）

- FAMBOX らしさをシステムで保証

**含意：**
- このフレーズが Purpose の "Single Source of Truth"
- README, ARCHITECTURE, memory すべてここに収束させる
- すべての判断は「これは Purpose に近づくか」で測る

## D-017｜2026-05-26｜ポジショニング：Middle & Fast

**決定：** 宮川さんの目指すポジショニングは「**Middle & Fast**」。

```
              狭　　　　　　　　　　　　　広
          ┌─────────────────────────────────┐
   速 ↑   │ Deep & Fast  │★Middle & Fast│ Wide & Fast │
        │              │  (宮川さん)  │  (Marc)     │
        ├─────────────────────────────────┤
        │ Deep & Slow  │ Middle&Slow │ Wide & Slow │
   遅 ↓   │ (従来宮川さん)│              │             │
          └─────────────────────────────────┘
```

**Middle の意味：**
- 1事業（FAM BOX 単体）固定ではなく、関連するブランド群（FAM / Lemon / 将来の類似ブランド）に展開可能
- でも Marc のように「多数の無関係なサービス」までは広げない
- マルチブランド対応の基盤になる中間ポジション

**Fast の意味：**
- Marc と同等の速度（10倍速）
- 環境 + プロンプト技術を Marc から学んで左側用に翻訳

**訂正履歴：**
- 当初「Deep & Fast」と Claude が提案 → 宮川さんから「Middle & Fast」に修正
- マルチブランド対応の長期構想（D-008）と整合させるため

**理由：**
- D-008（マルチブランド化は FAMBOX 1.0 後）との整合
- 完全な Deep だと FAM 専用で他に応用できない
- 完全な Wide だと Marc と被るし、宮川さんの強み（ブランド深さ）が活きない
- Middle が一番現実的かつ長期価値が高い

## D-018｜2026-05-26｜Step 2 インプット設計（Standard 形式）

**決定：** Step 2 の依頼書フォーマットを以下に確定する。

**形式：Standard（30分で書ける B レベル）**

**項目：**
1. **目的（Purpose）**：ビジネスゴール + 成功定義
2. **ターゲット（Target）**：ペルソナ + 心理状態
3. **ジャーニー（Journey）**：前 → このページで → 次
4. **メッセージ（Message）**：主訴求 + サブ + 避けたい表現
5. **制約（Constraints）**：期限 + 形式 + 文字数
6. **参照（References）**：自社過去 + 外部 + NG例

**運用条件：**
| 項目 | 値 |
|---|---|
| 依頼者 | 須藤・松浦・三宅・マレルチーム・安原さん 他 |
| 頻度 | 週5件（チーム全体合計） |
| 媒体 | Slack |

**重要原則：**
- 背景情報（FAM Brand DNA / DS / 過去資産）は依頼者が書かない。**インフラが自動付与**
- 依頼者が書くのは「**今回固有の情報**」のみ
- Slack ワークフロー or フォーム化を検討（毎回コピペ不要に）

**緊急時のバックアップ：** Lite 版（5分で書ける）も用意（急ぎのアイデア出し用）

**含意：**
- インフラ側に「ブランド永続情報レイヤー」を組み込む必要がある
- Step 1 で宮川さん自身が使ってみて、Standard で不足/過剰がないか検証する
- 検証結果を Step 2 開始時に微調整

## D-020｜2026-05-26｜「7割 / 3割」の境界定義

**決定：** AI が担う 7割と、人間が担う 3割を以下に定義する。

**AI が担う 7割：**
| カテゴリ | 内容 |
|---|---|
| 構造 | レイアウト、グリッド、要素配置 |
| ブランド準拠 | 色 / Poppins+Hiragino / DS v0.5 / bugs.md 規律 |
| 初稿コンテンツ | コピー叩き台、見出し候補、CTA バリエーション |
| アセット配置 | 画像・アイコン・パターンの当てはめ |
| コード/HTML | Liquid セクション、CSS、構造 HTML |

**人間が詰める 3割：**
| カテゴリ | 内容 |
|---|---|
| コピーの魂 | ブランドの "らしさ" の最終調整 |
| 画像の最終選定 | AI 候補から「これ」を選ぶ判断 |
| 案件固有の事情 | 「今回は○○さんに配慮」等の文脈 |
| 最終品質チェック | 公開前目視 + bugs.md lint 通過確認 |

**理由：**
- 「7割」を曖昧にしておくと、人によって意味が違ってバラつく
- 明確な境界線があれば、AI と人間の役割分担が議論しやすい
- Step 1〜3 すべてでこの境界線を維持
- Marc に説明する時の共通言語にもなる

## D-021｜2026-05-28｜AI/Human をカテゴリベースに再定義（D-020 を上書き）

**決定：** AI と人間の境界線を、パーセンテージ（70/30）ではなく **作業カテゴリ** で定義する。

**新しい4カテゴリ：**

| カテゴリ | 主体 | 具体例 |
|---|---|---|
| **AI proposes（提案）** | AI | 構造、レイアウト、ブランド準拠、初稿コピー、CTA バリエーション、コード |
| **Human validates（承認）** | 人間 | bugs.md 規律通過、ブランド整合性、出荷判定 |
| **Human adjusts（微調整）** | 人間 | コピーの魂、画像最終選定、案件固有事情の反映 |
| **Human decides（決定）** | 人間 | 複数案からの選択、戦略判断、出荷可否 |

**Marc の指摘（2026-05-28 フィードバック）：**
> 「percentages quickly become abstract. In the long run, more sustainable to frame it as categories of work: 'AI proposes', 'human validates / adjusts'」

**D-020 を上書きする理由：**
- 「70%/30%」は時間が経つと意味が曖昧になる
- カテゴリ定義の方が長期的に持続可能
- Step 2/3 で非デザイナーが入ってきた時に役割分担が明確
- 「AI proposes / Human validates」は普遍的なフレーミング

**含意：**
- bugs.md ルール違反検知 = "validates" 段階で機械化可能
- 「魂の調整」と「文脈反映」は明確に「adjusts」段階
- プロジェクト別の境界（D-022 後述）も同じ4カテゴリで記述

## D-022｜2026-05-28｜Learn 層を Step 1 から保護する

**決定：** Learn 層を Step 3（2027-Q1）まで放置せず、**Step 1 から最小機構を必須化** する。

**Marc の警告（2026-05-28 フィードバック）：**
> 「Sense and Learn are probably doing most of the real work. Generate and Reach are the most visible parts, but also the easiest. **If Learn isn't protected, the system risks producing faster without actually learning better.**」

**最小機構（Step 1 から必須）：**

| トリガー | アクション |
|---|---|
| Generate で失敗（出荷不能 / 大きな修正必要） | bugs.md に候補エントリを追加 |
| 同じ修正を 2回説明（Marc の M2 原則） | 即座に bugs.md にルール化 |
| 月1回 | bugs.md 追加件数を可視化（停滞検知メトリクス） |
| 金曜事業開発 | **「今週の Learn 進捗」を発表項目に追加** |

**理由：**
- Generate が回り始めると「速くなった」と満足してしまうリスク
- Learn が遅れても気付かない構造になりがち
- bugs.md の更新停滞 = 学習停滞 = システムが化石化

**含意：**
- 金曜事業開発の発表テンプレに「今週の Learn 進捗」を恒久的に追加
- bugs.md の更新ペース自体が KPI
- Marc の bugs.md パターン（Archeco V1-V51 index）から学ぶ

**この決定が D-016（3段階モデル）に与える影響：**
- Step 3 は「Learn 完成」ではなく「Learn が自走化」
- Step 1〜2 でも Learn は最小機構で常時稼働

## D-023｜2026-05-28｜DNA に Evolution Triggers を明文化

**含意：**
