# バイブコーディング6原則 — 本番リリース前に守るべき作法

## なぜ重要か

生成AIによる開発の民主化を肯定しつつ、「動くものができた」と「本番運用できる」の間にある **プロフェッショナルな最低ライン** を提示する論考。素人バイブコーディング勢が陥りがちな落とし穴を、エンジニア歴20年の視点で6つに整理。

ARCHECO/FAMBOX のShopifyテーマ・カスタムアプリ開発でも、Claude Code等で素早く形にした後の **本番投入前チェックリスト** として直接転用可能。

## 6原則

### 1. セキュリティ — 絶対に譲るな

| 落とし穴 | 対策 |
|---|---|
| シークレットをコードにハードコード | **環境変数**（.envは.gitignore必須） |
| APIキー漏洩は「いつか起きる」 | キーローテーション・監視・最小権限 |
| 「ログインできる」=「権限正しい」と思い込む | **IDOR防御をサーバサイドで実装**（他ユーザーデータの閲覧不可をAPI側で検証） |
| エラーメッセージで内部情報露出 | 本番エラーは汎用メッセージに |
| 社内システムだから油断 | **社内こそ重要**（攻撃者は内部にもいる） |

### 2. コスト — 事前見積もり・定期確認必須

- LLM API・クラウド・SaaSの **料金体系を読み込む**
- 想定リクエスト数 × 単価 で月額試算
- 定期的に請求ダッシュボードを確認（自動アラート設定）
- 暴走時の上限設定（rate limit、budget alert）

### 3. 法務 — 最初に確認

- 著作権（学習データ、生成物の権利関係）
- ライセンス（依存ライブラリのGPL混入等）
- 個人情報保護（保存・処理・越境移転）
- **後から直せない問題**なので、設計前に確認

### 4. データ構造 — 変更困難性を理解

- スキーマは「後から直せばいい」が一番効かない領域
- 正規化レベル、ID設計、関連の方向性を **最初に決める**
- マイグレーション戦略（ダウンタイム、ロールバック、データ整合性）

### 5. パフォーマンス — 規模を見積もれ

- 同時アクセス想定数、データ量、レスポンス目標
- N+1クエリ、不要なJOIN、キャッシュ戦略
- 本番相当データでの負荷テスト

### 6. 先人の失敗から学べ

- ライブラリ選定: **更新日時 / スター数 / ライセンス / Issueの傾向** を確認
- ステージング環境で検証 → 本番展開
- **故障時の復旧リハーサル** まで計画に含める

## ARCHECO/FAMBOXでの応用ポイント

| 場面 | 適用 |
|---|---|
| FAMBOX診断ウィザード等のカスタムアプリ | 顧客データ取扱いは原則3＋1（IDOR防御） |
| Liquidセクションでの動的データ取得 | metafield参照の権限境界を確認、`customer.id` のクライアント露出に注意 |
| Claude Codeで素早くプロトタイプ | 「動いた」で止めずに本ノートの6原則を通す |
| GA4・自動レポート系（projects/analytics） | サービスアカウント鍵の取扱い・ローテーション、コスト監視 |
| Seal Subscriptions等の外部連携 | API鍵管理 + Webhook検証 + リトライ戦略 |

## チェックリスト（本番投入前）

- [ ] シークレットがコードに含まれていない（grep確認）
- [ ] 認可チェックがサーバサイドで動いている（IDOR耐性）
- [ ] 想定外のリクエストでエラーメッセージから内部情報が漏れない
- [ ] 月額コストの上限見積もりとアラート設定済み
- [ ] 依存ライブラリのライセンス監査済み
- [ ] 個人情報の保存先・保持期間が明示されている
- [ ] スキーマ変更時の手順が文書化されている
- [ ] 本番相当データでの動作確認済み
- [ ] ロールバック手順がテスト済み
- [ ] 監視・ログ・通知が機能している
