## Slide 3 / 20 — AI 制御の進化系譜

# 「指示」から「構造」へ — AI 制御の3世代

| 世代 | 方式 | 弱点 |
|---|---|---|
| 第1世代: CLAUDE.md | お願い（プロンプト） | **守られない**。守らせる仕組みがない |
| 第2世代: AGENTS.md | 取り決め（合意） | **検証されない**。違反を検出できない |
| **第3世代: ハーネス** | **構造的制御** | — |

ハーネスエンジニアリング = **馬具（harness）が馬の能力を最大限に引き出すように、5層の制約と検証で AI を正しい方向へ導くアーキテクチャ設計**。

出典: nogataka「ハーネスエンジニアリング入門」Qiita 2026-03 / GMO Internet ConoHa VPS 実装 / everything-claude-code（GitHub 100K+ stars）

> **話すこと**: AI に「これやって」と頼むだけでは、ブランドの一貫性は崩れます。
> ハーネスは「お願い」ではなく「構造」。違反を構造的に捕まえることで信頼を担保します。
> これは既に世界の先進事例で実証されたパラダイムです。

## Slide 4 / 20 — ハーネスの5層

# ハーネスの5層構造

```
┌──────────────────────────────────────────┐
│  1. ルール       — 行動規範の宣言        │
│  2. スキル       — 再利用可能な手順書    │
│  3. フック       — イベント駆動の自動実行 │
│  4. メモリ       — セッション間の文脈    │
│  5. フィードバック — 多層の検証スイート   │
└──────────────────────────────────────────┘
        ↑                       ↑
   [人間が設計]           [人間が監督]
```

5層すべてが揃って初めて、**ブランドの一貫性が構造的に守られる**。

> **話すこと**: ルールは「何をすべきか」、スキルは「どうやるか」、フックは「いつ動くか」、メモリは「過去をどう覚えるか」、フィードバックは「結果をどう検証するか」。
> 5つが揃って初めて、AI が暴走せず、ブランドからずれず、学習し続ける構造になります。

## Slide 10 / 20 — Experience Flywheel

# ハーネスが回し続ける構造 — Experience Flywheel

```
       ┌─→ Sense（感知）─────────┐
       │   在庫モニター + 異常検知       │
       │                                ↓
   Run（学習）                  Generate（生成）
   反応データから              栄養計算 +
   プレーブック更新            メニュー組み立て
       ↑                                │
       │                                ↓
       └─── Reach（実行）───────────────┘
           配送最適化 + 顧客通知
```

- **Sense / Generate / Reach** = Layer 3 フック層の実体
- **Run** = Layer 4 メモリ層 + Layer 5 フィードバック層
- 全体を束ねる **オーケストレーター** が AI 同士の整合性を確保

→ **5+1 のエージェントは、ハーネスの「動く部品」**。

> **話すこと**: エージェントを5つ並べる構想に見えますが、本質はフライホイールが回り続けることです。
> 1周回るごとに学習が深まり、FAMBOX 独自の最適化が積み重なります。
> 他社では再現できない資産になります。

## Slide 11 / 20 — 統合の例：食材断絶への即時対応

# ハーネスが3秒で動く例

```
[Sense] 在庫モニターが鶏胸肉の入荷停止を検知
   ↓ ルール層 (Verbal/Brand DNA) を参照
[Generate] 栄養計算が代替食材で同等PFCのメニューを生成
   ↓ メモリ層 (Decision Trace) を参照
[Generate] 顧客嗜好で各顧客の許容範囲に絞り込み
   ↓
[Reach] 配送最適化が既存配送計画への影響を再計算
   ↓
[Reach] 顧客通知が「明日のメニュー変更」を個別送信
   ↓
[Run] 顧客反応を回収 → 次回の代替案精度を上げる
   ↓ フィードバック層で LLMO/Lighthouse 監査
[人間] 重大なら最終承認、通常なら事後レビューのみ
```

総処理時間: **3秒〜数十秒**（人手では数時間〜数日）。

> **話すこと**: 各ステップでハーネスの 5 層を必ず通過します。
> ルール・メモリ・フィードバックが組み込まれているので、AI が暴走したりブランドからずれたりしない構造です。

## Slide 12 / 20 — 6番目のエージェント：LLMO 監査

# 6番目のエージェント — LLMO 監査（Run層）

**役割**: 全ての公開コンテンツを LLMO 観点で自動監査し、AI 引用可能性を最大化。

AI関連ボットが HTML リクエストの **4.2%** を占有（Cloudflare 2026）。Google 混合で **7-10%** 予想。
→ **AI 経由の認知は無視できない流量** になっている。

**自動チェック項目（8つ）**:
- ✅ 結論先行（最初1-2文 ≤ 200字）
- ✅ 質問形 / 定義形の見出し
- ✅ 依存表現（上記の通り 等）ゼロ
- ✅ 抽象表現（多くの 等）ゼロ
- ✅ JSON-LD（Organization + Article）
- ✅ セマンティック HTML 構造
- ✅ 著者バイライン
- ✅ 出典リンク

**実装状態（2026-05-21）**:
LPB v4 に LLMO Check API 実装済 — Phase 1 と並行して即運用可能。

> **話すこと**: ハーネスの「フィードバック層」の中核です。
> 視覚側の Brand Intelligence が Animation Library / DNA 軸なら、テキスト側の Brand Intelligence が LLMO Check です。
> 既に動く実装があるので、Phase 1 着手と同時に既存ブログのリライトから始められます。

## Slide 13 / 20 — 致命的領域は必ず人間

# ガードレール — 致命的領域は人間が握り続ける

| 自動で動かす | 必ず人間が判断 |
|---|---|
| 在庫モニター・栄養計算・通常配送 | **アレルギー誤配送ゼロの確認** |
| 異常検知・仮説生成・通常通知 | **重大インシデント時のエスカレーション** |
| 通常時のメニュー組み立て | **季節キャンペーン・新商品の方針** |
| 文脈学習・プレーブック更新 | **新ルール採用 / 棄却** |
| LLMO 監査・修正提案 | **公開コンテンツの最終承認** |

**安全弁の原則**:
1. 致命的領域（アレルギー・契約・財務）は必ず人間
2. ガードレールは事前に FAMBOX 運営チームが設計
3. AI の自律行動はログ化・遡及可能（Decision Trace）

> **話すこと**: ハーネスは「信頼しない仕組み」ではなく「信頼を構造で担保する仕組み」です。
> 人間が「事後チェック」ではなく「事前構造」で安全弁を握ります。

## Slide 14 / 20 — Human-in-the-Lead

# 人間の役割は「設定者」へ進化する

| 段階 | 人間の役割 |
|---|---|
| Human-in-the-Loop（旧） | ループ内で判断・実行 |
| Human-on-the-Loop（Phase 1-2） | ループ外で監督 |
| **Human-in-the-Lead（Phase 3+）** | **目的・倫理・文脈の設定のみ** |

**Phase 3+ 後の須藤さん・宮川さんの役割**:
- 🎯 **目的設定** — FAMBOX は何のために動くか

- 📚 **文脈設定** — どの背景で動くか（ブランド・組織のコンテキスト）

それ以外はハーネスが回す。

> **話すこと**: 人手を不要にする話ではありません。
> 人間の時間を「設計・判断・関係性」に集中させる構想です。
> 須藤さんの役割は事務作業から、FAMBOX の方向性そのものを定義する立場に進化します。

## Slide 15 / 20 — Phase 1: 着手位置

# Phase 1（最初の3ヶ月）— フック層 + フィードバック層から

**着手対象**:
- 🔧 **Layer 3 フック**: 在庫モニター + 異常検知エージェントの最小版（Sense）
- 🔧 **Layer 5 フィードバック**: LLMO Check で既存ブログ上位3記事リライト

**選定理由**:
- 完成度の低い2層に同時着手 → ハーネス全体が一気に回り始める
- 効果が **見えやすい**（食材ロス削減 / AI 引用率向上）
- 致命的領域に踏み込まない（人間判断を残せる）
- 既存実装（LPB LLMO Check）を流用 → 立ち上がり高速

**3ヶ月後の目標**:
- 月間食材ロス: 現状値の **-30%**
- 入荷遅延の検知時間: 24時間 → **1時間**
- 在庫確認作業: 週5h → **週1h**
- AI 引用率（定点測定）: **+15%**

> **話すこと**: Phase 1 は「機能の試作」ではなく「ハーネスの最小構成立ち上げ」です。
> フック層 1個 + フィードバック層 1個 が動けば、すでにハーネスは回ります。
> ここで価値が見えてから、Phase 2 以降に拡張します。
